# roost bridge in Firefox

*2026-10-19. Issue [#177](https://github.com/PeterKnego/roost/issues/177),
which carries the problem and the shape. This records what implementation
settled, and the three things that moved it.*

## What it is

The same extension, with the same tools, consent window, key, deny-list and
handoff, built a second time for Firefox: the release ships
`roost-extension-<version>-firefox.zip` beside the Chrome zips. roost,
`roost mcp`, the relay and the signed payload are unchanged. None of them
knows which browser answers.

## One tree, two backends

Firefox has no `debugger` API (bug 1316741), and the Chrome extension drove
everything through it. So the driving moved behind `drive`:

- `extension/page.js`: everything that runs *inside* a page, as one
  self-contained function, `roostPage(op, a)`. It is one function because each
  is serialised alone: Chrome sends its source over the DevTools protocol, and
  Firefox's `scripting.executeScript` takes a function and never a string.
- `extension/drive-cdp.js`: Chrome's backend. It is the old code, unchanged
  in behaviour, now calling `roostPage` instead of string scripts.
- `extension/drive-page.js`: Firefox's backend.
  - read, click, type and upload run `roostPage` through
    `scripting.executeScript`;
  - screenshots come from `tabs.captureTab`, which takes a background tab;
  - the console is a hook injected into the page's own world, re-injected on
    every load of a watched tab.
- `worker.js` picks the backend by whether `chrome.debugger` exists. Chrome
  loads the files with `importScripts`. Firefox lists them in
  `background.scripts`, which the packer reads from that same `importScripts`
  line, so the two browsers cannot load different files.

## The Firefox manifest

Generated by `scripts/package-extension.sh` from the one `manifest.json`:
- `background.scripts`, not a service worker (Firefox has none);
- no `debugger`, and no `drive-cdp.js` in the zip (AMO's linter flags it, and
  Firefox never runs it);
- `optional_host_permissions: ["<all_urls>"]` (`tabs.captureTab` names it);
- `gecko.id: roost-bridge@roost`, `strict_min_version: 140.0`,
  `data_collection_permissions.required: [websiteContent, browsingActivity]`.

`web-ext lint`: 0 errors. The one warning is about Firefox for Android,
which is not targeted (no popup windows for consent); uncheck Android on
submission.

## What moved the design

1. **The minimum is 140, not 128.** The issue proposed 128 as the ESR. But
   `data_collection_permissions`, which AMO requires of new add-ons, arrives
   in 140, and 140 is the current ESR. MAIN-world scripts (128) and tab groups
   (139) come with it.
2. **Firefox match patterns take no port** (bugs 1362809, 1468162). A roost
   at `http://127.0.0.1:8444` is registered and granted as
   `http://127.0.0.1/*`. The worker still checks the sender's whole origin,
   port included, so a page on another port of the same host can talk to the
   content script and be refused.
3. **Site access is asked for from the consent window.** Firefox's
   backend needs the optional `<all_urls>`. `permissions.request` is honoured
   only from a user gesture in an extension page, which the consent window's
   Allow click is. It is the handler's first call, because any `await` before
   it ends the gesture. The options page has an explicit button as well.
   Without the grant, every tool that needs it says how to give it.

## Differences that remain, and where they are said

| | Chrome | Firefox | where Claude learns it |
|---|---|---|---|
| click, type | trusted input via the DevTools protocol | dispatched events (`isTrusted: false`) | the tool description, and each result's `note` |
| upload through a picker-opening button | intercepted and filled | impossible | the description, and the error |
| console | from first attach, across loads | from first `chrome_console`, per load | the result's `note` |

The tool names stay `chrome_*`. Renaming would break every prompt that uses
them, and the descriptions now say "the user's own browser, Chrome or
Firefox".

## A bug the Firefox test found in both browsers

The content script could run twice in one page: once registered, once
injected by the worker when the address list changes, if the page loaded in
between. Both copies forwarded every call. The second was refused as a replay
("that call was already handled"), and that refusal could reach roost before
the real answer. `content.js` now runs once per page. A copy orphaned by an
extension reload reports itself dead and does not keep its successor out.

## Testing

`tests/browser/bridge-firefox.mjs` installs the release's Firefox package
into a real Firefox over Marionette, which is not CDP. WebDriver BiDi can
install an extension but refuses to open any moz-extension page, and so does
Marionette's content context. Marionette's privileged context, on a test
profile started with `--remote-allow-system-access`, grants the site access
and writes the extension's storage, the way Firefox's own extension tests do.

The consent window cannot be driven at all, so the Firefox test runs in
unsafe mode. The consent logic is shared and covered by `bridge.mjs`. What is
Firefox's own about it, the Allow click asking for site access, is not
reached by any automated test, and is said so in the test's header.
